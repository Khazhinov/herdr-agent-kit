# herdr-tool-agents

[English](README.md) | Русский

Реестр папок машины, в которых настроены MCP-серверы, и CLI, через который любой агент в любом
проекте пользуется этими серверами при помощи дешёвого агента-исполнителя в терминале
[herdr-core](https://github.com/herdrdev/herdr-core). Не привязан к одной среде: модулем может быть
папка Claude Code, Codex или OpenCode либо любая команда, которой управляет herdr-core. Работает
вместе с [herdr-gsd-template](https://github.com/Khazhinov/herdr-gsd-template) (`orch.py tools`,
`tools-link`, `tool-ask`), но от него не зависит.

## Назначение

Агент проекта со многими MCP-серверами загружает сотни схем инструментов в каждый запрос, а каждому
проекту нужна своя копия токенов. Здесь MCP-серверы остаются в своих папках. Реестр описывает их один
раз; проект хранит только короткий список имён инструментов и способ вызова. Вызов уходит постоянному
исполнителю на самой дешёвой модели поставщика этой папки; агент проекта читает короткий файл ответа.

| Свойство | Как обеспечено |
|---|---|
| Контекст проекта не растёт | `.agent-tools/TOOLS.md`: имена инструментов по модулям; параметры по запросу (`card <module> <tool>`) |
| Точные описания инструментов | `refresh` запускает каждый MCP-сервер из конфигурации самой папки и читает `tools/list`; LLM не участвует |
| Любая среда | встроены `claude`, `codex`, `opencode` (команда запуска, флаг модели, сброс); любая другая - `command`, `reset`, `mcp_config`. Формат MCP-конфигурации определяется по содержимому (`mcpServers`, `servers`, `mcp`, `[mcp_servers]`) |
| Дешёвая модель для вызовов | `model` модуля (например, младшая модель поставщика) |
| Секреты в одной папке | серверы и токены только в папке модуля; проект получает возможность, а не токен |
| Проекты следуют изменениям реестра | реестр помнит подключённые проекты; `sync` переписывает их `TOOLS.md` при изменении карточки |
| Запись только с согласия человека | `--write` работает при `allow_write = true`; запрос помечается `WRITE ALLOWED BY USER` |
| Аудит | `~/.cache/herdr-tool-agents/audit.jsonl` |

## Состав

| Путь | В git | Назначение |
|---|---|---|
| `tool_ask.py`, `mcp_probe.py` | да | CLI, чтение конфигураций MCP и клиент `tools/list` (только стандартная библиотека) |
| `registry.example.toml` | да | пример записи реестра с пояснениями |
| `examples/<module>/` | да | образец конфигурации MCP для папки модуля |
| `AGENTS.md` | да | порядок работы агента, который ведёт реестр |
| `local/registry.toml` | нет | модули этой машины |
| `local/cards/<module>.md` | нет | сгенерированные карточки инструментов |
| `local/modules/<module>.md` | нет | дополнительные правила исполнителя модуля |
| `local/links.json` | нет | подключённые проекты и их модули |

В подключённом проекте: `.agent-tools/TOOLS.md` (исключён через `.git/info/exclude`, в git не
попадает) и одна строка-указатель в `AGENTS.md` (и в `CLAUDE.md`, если он не подключает `AGENTS.md`)
без путей машины.

## Настройка на машине

Порядок одинаков для автора и для того, кто клонировал репозиторий; свежий клон начинается с пустого
`local/`.

1. Установить [herdr-core](https://github.com/herdrdev/herdr-core) (`hc`) и среды агентов, которые
   используются в папках модулей.
2. `mkdir -p local && cp registry.example.toml local/registry.toml`, удалить пример записи.
3. `./tool_ask.py scan <root>` перечисляет папки внутри `<root>` с конфигурациями MCP в стандартных
   местах Claude Code, Codex, OpenCode, Gemini CLI, Cursor и VS Code и имена серверов. Другие среды:
   зарегистрировать папку с `mcp_config`.
4. Зарегистрировать нужные папки (вручную или поручить агенту в этой папке: он следует `AGENTS.md`):
   идентификатор, `workdir`, `runtime`, `model`, `description`, необязательный фильтр `tools`,
   `allow_write`.
5. `./tool_ask.py refresh --all`, затем `./tool_ask.py list` и `./tool_ask.py card <module>`.
   Сервер, который не запустился, отмечается в карточке; остальные работают.
6. Пробный вызов: `./tool_ask.py ask <module> "<узкий запрос>"`. Первый запуск исполнителя может
   ждать диалога доверия или входа: ответить в Herdr App.

## Подключение проекта

```bash
./tool_ask.py link /path/to/project gitlab-main youtrack   # или из проекта на herdr-gsd-template:
python3 scripts/orch.py tools-link gitlab-main youtrack    # путь к реестру: HERDR_TOOL_AGENTS или [tools] hub
```

Агент проекта читает `.agent-tools/TOOLS.md` и вызывает `tool_ask.py ask <module> "<запрос>"`.
Коды выхода: 0 ответ готов, 1 ошибка или таймаут, 2 конфигурация, 3 модуль занят, 4 нужен человек,
5 запись запрещена.

## Поддержание проектов в актуальном состоянии

После изменения сервера, его конфигурации или реестра:

```bash
./tool_ask.py refresh <module>      # или --all
./tool_ask.py sync --dry-run        # какие подключённые проекты изменятся
./tool_ask.py sync                  # переписать их TOOLS.md
```

`sync` также сообщает о подключённых проектах, которых больше нет, и о модулях, удалённых из реестра.
`unlink <project> [module...]` удаляет подключение.

## Особенности сред

Полный цикл (запуск, сброс, вызов MCP, файл ответа) проверен для Claude Code, Codex и OpenCode.

| Среда | Однократно для папки модуля |
|---|---|
| Claude Code | ответить на запрос доверия к папке при первом запуске |
| Codex | папка - доверенный проект (`[projects."<workdir>"] trust_level = "trusted"`), иначе её `.codex/config.toml` и MCP-серверы не загружаются; изменённые глобальные hooks однократно запрашивают доверие при запуске |
| OpenCode | разрешить запись ответов вне папки: `"permission": {"external_directory": {"<home>/.cache/herdr-tool-agents/**": "allow"}}` в `opencode.json` папки |
| Другая | `command` (полный argv с дешёвой моделью), `reset`, `mcp_config`, если конфигурация не в стандартном месте; проверить собственные запросы доверия и разрешения каталогов среды |

Исполнитель, ожидающий такого запроса, приводит к выходу `ask` с кодом 4; ответ даёт человек в Herdr
App или через `hc attach tool-<module>`, агент за человека не отвечает.

## Протокол запроса

1. Терминал исполнителя `tool-<module>` запускается при первом запросе в папке модуля и продолжает
   работать.
2. Перед каждым запросом исполнитель получает сброс своей среды (`/clear` или `/new`): один запрос -
   один разговор.
3. Запрос содержит правила исполнителя, путь к файлу ответа и режим: только чтение или
   `WRITE ALLOWED BY USER`. Правила передаются вместе с запросом, поэтому любая среда получает их
   одинаково.
4. Завершение определяется по последней строке файла ответа (`DONE` или `FAILED: ...`) и событиям
   herdr-core.
